## 1. 요약 (목표와 범위)

**목표:** 서버 재배포(롤링 업데이트·단일 재기동) 중 통화 참가자가 3분 대기 시간 안에 방에서 튕기지 않고 자동으로 같은 방에 복구되게 한다. 3분이 지나도 복구되지 않으면 모두 방 목록으로 보내는 기존 스펙은 유지한다.

**범위 (사용자 확인 완료):**

| 구분 | 원인 | 수정 방향 |
|---|---|---|
| H6 | 새 인스턴스는 기동 직후 수 초간 다른 인스턴스를 모름 → 살아 있는 owner 의 방을 "주인 없음"으로 보고 비활성화 | 인스턴스 생존 판정을 모든 인스턴스가 공유하는 Redis heartbeat 기준으로 변경. 방 비활성화는 owner 사망이 heartbeat 로 확정된 경우에만 |
| H1 | 인스턴스 쿠키 수집 전에 READY → 복구 API 가 "쿠키 미준비" → 프론트가 약 1.5초 만에 방 목록 이동 | 빠른 재시도 3회는 유지, 소진 시 방 목록 대신 기존 재연결 루프(최대 약 3분)로 넘김. 서버에 미준비 응답 로그 |
| H2 | 다른 살아 있는 인스턴스가 이미 claim 한 방에 복구 요청 → "복구 불가"로 방 목록 이동 | owner 인스턴스 쿠키를 내려주고 성공으로 응답해 그쪽으로 재연결 |
| H3·H5 | 종료 정리가 Spring 종료와 병렬 실행 → 서버 종료 알림 누락 가능 → 죽은 인스턴스로 리다이렉트 새로고침 반복 후 퇴장 | 커스텀 JVM 종료 훅 제거, Spring 종료 이벤트 안에서 순서대로 정리, 방 단위 실패 격리, 종료 알림·인스턴스 정보 삭제는 항상 수행. 재연결 중 리다이렉트는 새로고침 대신 재연결 |
| A1 | 곧 종료될 인스턴스가 방을 claim → 같은 배포에서 반복 끊김 | 종료 중 인스턴스는 claim 하지 않고 재시도 응답 |
| H4 | 복구 metadata TTL(종료 시작 기준)과 화면 대기(끊긴 뒤 기준) 기준점 차이로 3분을 다 기다리지 못함 | `recovery.room.ttl-seconds` 240 (운영 적용 완료, 코드 기본값·로컬 설정 반영) |
| H7 | 방 삭제 배치(매시 0·30분)가 ACTIVE 가 아닌 방을 모두 영구 삭제 → 종료 정리로 CREATED 가 된 복구 대기 방이 배치와 겹치면 삭제 | 유효한 복구 metadata 가 있는 방은 배치 삭제 대상에서 제외 (계획 수립 중 추가 확인한 동일 부류 결함) |
| MIC | 재연결 시 새로 연 마이크·카메라 트랙 기본값이 켜짐 → UI 는 꺼짐인데 소리가 나감 | 새 트랙에 기존 켬/끔 상태 재적용 |
| 기타 | 재연결 중 방 정보 조회 실패를 무시 → 오버레이만 뜬 채 멈춤 | 재연결 루프로 수렴 |

## 2. 영향도 분석 (중요)

- **backend (`springboot-backend`)**
  - 방 입장 조회·복구 API 의 owner 생존 판정과 응답 분기 (H6·H2·A1·H1 로그)
  - 인스턴스 생존 조회(Redis heartbeat) 추가
  - 종료 정리 실행 시점·순서·예외 격리 (H5) — 녹화 partial marker 기록 순서가 같은 경로에 있어 recording 도메인(L3) 영향
  - 방 삭제 배치의 복구 대기 방 제외 (H7)
  - 복구 metadata TTL 기본값 240 (H4)
- **frontend (`nodejs-frontend`)**
  - 재연결·복구 흐름(`rtc` — webrtc 도메인 L3): 복구 재시도 소진 처리, 재연결 중 리다이렉트·조회 실패 처리, 재연결 후 로컬 미디어 상태 재적용
  - 판단 로직을 브라우저·Node 겸용 순수 함수 파일로 분리하고 `node:test` 단위 테스트 추가
  - 채팅방 템플릿에 새 스크립트 로드 추가
- **desktop (`chatforyou-desktop`)**: 소스 직접 수정 없음. `npm run sync` 로만 반영
- **운영 설정**: `recovery.room.ttl-seconds=240` 은 사용자가 운영에 선반영
- **응답 계약**: 복구 API 에 재시도 사유 2종 추가(종료 중, owner 쿠키 미준비), "이미 다른 인스턴스가 복구"는 기존 SUCCESS 계약으로 표현 → 구 클라이언트도 재연결로 처리 가능

**변경 전 → 후 (사용자 체감)**

| 상황 | 변경 전 | 변경 후 |
|---|---|---|
| 새 Pod 쿠키 수집 중 재접속 | 약 1.5초 뒤 방 목록 | 3분 안에서 계속 재연결 |
| 새 Pod 기동 직후 멀쩡한 방 조회 | 방 비활성화 → 배치 영구 삭제 | 정상 라우팅 |

| 서버 종료 알림 누락 | 새로고침 4회 후 방 목록 | 알림 보장 + 재연결 중 새로고침 없음 |
| 재연결 후 음소거 | 몰래 풀림 | 유지 |

## 3. 기술과 리스크

- **L3 판정 근거:** `nodejs-frontend/static/js/rtc/**` (webrtc 도메인), 종료 정리·복구 서비스의 녹화 marker 키워드 (recording 도메인), Redis/Kafka 키워드(L2). 복합 규칙상 최고 등급 L3.
- **리스크**
  - Redis heartbeat 는 인스턴스가 비정상 종료하면 최대 90초 남는다 → 그 구간은 여전히 살아 있다고 판정(범위 밖 잔여). 정상 종료는 종료 정리에서 즉시 삭제.
  - 종료 알림을 앞당기면, 종료 중 인스턴스가 방 상태를 되돌리는 쓰기와 새 인스턴스의 claim 이 겹칠 수 있다 → 방 초기화 루프를 먼저 끝낸 뒤 알림·삭제를 수행하는 순서를 유지.
  - 커스텀 JVM 훅 제거 시, Spring 컨텍스트 종료 이벤트가 오지 않는 종료 경로에서는 정리가 실행되지 않는다 → Spring Boot 기본 종료 훅(SIGTERM/SIGINT)이 컨텍스트를 닫으므로 운영 경로는 유지됨을 테스트·설계로 명시.
  - 재연결 중 리다이렉트를 재연결로 처리해도 서버 `room-redirect-count` 3회 초과 방어는 그대로 동작해야 한다(라우팅 루프 차단 유지).
  - 복구 재시도와 재연결 재시도가 중첩되면 폭주 → 한 시점에 하나의 루프만 돌게 인계 방식으로 설계.
  - 프론트 규약상 브라우저 모듈(import/export) 금지 → 전역 노출 + CommonJS 조건부 export 로 Node 테스트.
- **검증 전략:** 백엔드 JUnit(Mockito) 단위 테스트, 프론트 `node:test` 단위 테스트, `scripts/verify-changes.sh` L3 게이트, desktop sync 확인, Phase 05 codex 교차 리뷰(webrtc·recording 프로토콜).

## 4. 최종 결론 및 UX 가이드

- 사용자는 재배포 중 "서버 패치가 진행 중입니다" 오버레이만 보고, 3분 안에 같은 방으로 자동 복귀한다.
- 3분 안에 복구되지 않으면 기존처럼 "연결 실패" 모달로 재입장을 안내한다(스펙 유지).
- 재연결 뒤 마이크·카메라 상태는 끊기기 전과 같다.
- 구현 후 실제 재기동 재현 테스트는 사용자가 직접 수행한다.
